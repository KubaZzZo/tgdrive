# 视频播放与本机缓存

自动模式下，MP4 优先由浏览器原生播放。启动失败或 5 秒内没有可显示的首帧时，最多尝试一次兼容播放。手动选择兼容模式时先尝试兼容播放，失败后可自动回退到原生。手动选择浏览器原生时只使用原生路径。启动总预算为 15 秒，兼容探测的 64 KiB 请求和元数据补读各有 4 秒超时。播放器会记住手动选择的播放方式。

支持 MediaSource 的浏览器在兼容模式下可播放 H.264 / AAC 分片 MP4。对索引位于媒体数据之前的普通 H.264 MP4，兼容模式会在浏览器内按需重封装为分片，AAC 音轨一并保留，音视频均无需重编码。拖动到未缓冲位置时，播放器按文件索引从附近的关键帧读取。索引或编码不满足条件，或普通 MP4 重封装播放失败时，播放器会使用浏览器原生播放。也可以手动切换“浏览器原生”。编码本身不受浏览器支持时仍需下载到本地播放器观看。

iPhone 的兼容模式优先检测 ManagedMediaSource，在绑定视频源前禁用远程播放，并响应系统的缓冲窗口。旧实现只检测桌面 MediaSource，导致支持 ManagedMediaSource 的 iPhone 误退回原生分片 MP4 路径。此处通过能力检测选择接口，不依赖 iOS 版本或浏览器名称。

播放面板提供进度、快进快退、静音、下载、画中画和全屏。倍速、旋转、播放方式和本机缓存位于播放设置。横向视频在移动端进入全屏时会尝试锁定横屏，浏览器限制旋转时仍可横向铺满播放器。画中画入口随浏览器能力显示。

分片视频默认自动预缓冲。播放时根据吞吐和码率调整缓冲窗口，暂停或切到后台时缩短窗口。60 秒和 120 秒选项可提高播放时的上限，播放器仍会按码率限制内存使用。拖到未缓冲位置时，播放器取消旧读取，优先使用文件索引定位关键帧。缺索引时，单次探测最多请求 8 MiB 或等待 2.5 秒。预算内找不到可用关键帧且原进度仍有缓冲时，播放器返回原位置。传输断开后最多续接重试两次。

播放请求使用实际 Range 的首字节等待和读取耗时估算网速。缓冲不足时使用 512 KiB，请求稳定后按网速和码率调整到 512 KiB～4 MiB，按 64 KiB 对齐。浏览器缓冲配额不足时，先清理播放位置 10 秒前的数据，再重试写入同一段。后续 Range 请求携带初次响应的 ETag，文件版本变化时停止拼接，需重新加载视频。

文件下载前会检查登录、连接、分段记录和流量预算，播放器内会显示服务端返回的失败原因。下载提交后由浏览器下载列表管理进度。接口提供 ETag / If-Range 续传校验。文件版本不匹配时返回完整文件，避免新旧内容拼接。Telegram 连接中断、超时或短读时，从已发送字节处最多重试两次。跨 Telegram 分段的 Range 下载会按文件顺序合并。分享页的下载按钮直接保存媒体文件。

保存大文件时，单个 Telegram 分段内待读取的范围达到 8 MiB，服务端会先读取首块，再同时预读最多四个 512 KiB 块，按文件顺序发送。每个 Telegram 连接最多同时加速两笔下载。服务端收到断开通知后会取消尚未完成的预读。在线播放和小范围读取继续使用按需读取。

播放器优先使用文件头中可用的直接分片索引（SIDX）。需要探测时，同一浏览器标签页内重新打开同一版本的视频可以复用已找到的关键帧。

本机 OPFS 缓存保留已读过的分片 MP4 文件头，以及观看或跳转过程中读到的关键帧附近片段。每个视频最多保留 8 段，每段至多 1 MiB，重复访问的片段会更新淘汰顺序。重新打开分片视频会尝试恢复播放进度，匹配 ETag 的本机片段和关键帧索引可以跨页面刷新复用。

手动“缓存到本机”按网络速度使用 1～3 路请求，正在播放时降为单路。缓存预算为 512 MiB，手动缓存更大的单个视频时可扩展到该视频大小，仍受浏览器空间限制。重新打开视频时，仅在本机有完整文件或文件头缓存时单独发起权限和 ETag 校验。整片下载也逐段校验 ETag，正在播放的缓存受跨标签页锁保护。缓存完成后，下次打开时会优先使用本机文件。首次传输仍经 VPS，关闭播放器会取消未完成的缓存。

封面优先使用 Telegram 静态缩略图。缺少封面时，服务端用 FFmpeg 从最多 8 MiB 的文件开头提取静态帧。超出范围才可读取索引或关键帧的文件显示视频图标。图床列表使用服务端生成的最长边 320 像素的 WebP 缩略图。Docker 镜像包含 FFmpeg，原生部署需安装 `ffmpeg`。浏览器私有缓存使用 ETag 重新校验，登录仍有效且内容相同时服务端返回 304。

频道视频优先以视频自带说明的首个有效段落命名，多行合并为一行，跳过独立链接和标签行，保留原始视频后缀，最长 255 个字符。视频自身没有有效说明时，会读取同一个 Telegram 相册里唯一的共用说明，例如与视频一起发送的封面图片上的文字；存在多个不同说明时不会猜测。相册关联以 Telegram 的 grouped_id 为准，不借用相邻独立消息的文字。没有有效简介时保留原文件名。

编辑或移除频道说明时，自动名称会跟随更新；在网盘手动重命名后则保留自定义名称。已有文件会在完整频道扫描时补齐；升级时对无法确认来源的旧名称按自定义名称保留。相册完整到达后会再次同步，支持文字与视频分批到达。

回归检查：运行 `python -m pytest -q`；在 frontend 运行 `npm test` 与 `npm run build`。本机缓存的浏览器检查需先启动 Vite，然后分别用 Playwright CLI 的 chrome / msedge 会话打开 `http://127.0.0.1:5173/`，运行 `run-code --filename frontend/tests/deviceCache.browser.cjs`（从仓库根目录执行）。检查真实 OPFS 分段写入、字节完整性、重复读取、频道隔离与取消清理；使用约 6 MB 合成数据，不连接 Telegram。

视频浏览器回归从仓库根目录运行。先构建前端并准备 Python Playwright、Chromium 与支持 libx264 的 FFmpeg，然后执行 `python frontend/tests/video_seek_browser.py --runs 5 --play-ms 3000`。可用 `--ffmpeg` 指定 FFmpeg 路径，用 `--channel msedge` 使用已安装的 Edge，或加 `--mobile --delay-ms 350` 模拟窄屏和高延迟。脚本记录首帧、拖动、卡顿、定位流量与被取消请求已发出的字节，并汇总中位数与 P95。热缓存用例刷新页面后验证从磁盘续播。模拟结果应与真实线路和设备的样本分开解读。

浏览器控制台的 `[TG Drive] media startup` 调试日志记录响应头、首字节、探测结束、重封装准备就绪、媒体源开启及首帧可显示的时间。支持帧回调的浏览器也会记录首次提交画面的时间。兼容模式的探测日志含 `X-Request-ID`，可与服务日志中的 `Media probe` 对照。原生播放的首个范围由服务端记录为 `Media initial-range`，浏览器若提供 Resource Timing，也会记录首字节。取消请求时服务端日志记录已交给响应流的字节。

## 服务端切片缓存

设置 `MEDIA_CACHE_MAX_MIB=2048` 启用 2 GiB 缓存。`MEDIA_CACHE_MIN_FREE_MIB=4096` 保留 4 GiB 磁盘可用空间，达到阈值时停止写入并继续按需播放。缓存容量包含正在写入的切片，按最近访问时间淘汰旧切片。`MEDIA_CACHE_DIR` 默认位于 `DATA_DIR/media-slices`，可指定独立可写目录，并从数据备份中排除。

缓存只服务已登录的私有视频 Range 播放。缓存键包含工作区、文件 ETag 和切片位置。4 MiB 对齐的读请求覆盖至少半个切片时可以补齐剩余内容，按原 Range 逐步发送客户端需要的字节。小探测与未对齐的冷跳转仍按实际范围读取。命中缓存仍执行流量预算检查并计入 CDN 出站流量。

登录后可从 `GET /api/traffic` 的 `media_cache` 字段查看进程启动以来的切片命中次数、未命中次数、缓存发送字节和补齐切片产生的额外 Telegram 读取量。观察 `hit_bytes` 与 `overfetch_bytes` 的差值可估算缓存节省的回源流量。可结合媒体探测日志比较冷、热请求的首字节时间。
